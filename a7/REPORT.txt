Analysis of 3-way test

- Although the IP addresses and port numbers are not very human-readable, the "Reverse syncing" statements do include the full peer name.
  This reverse sync is fired off after a get_description request is received from a peer. It is in a separate thread and therefore avoids deadlock.
  Each peer in this example is talking to each other, as these statements reveal. Also, throughout the logs you can see the "Found 2 peer(s) in catalog" statements.

- Peer B and Peer C, started simultaneously on machine 10, do find each other and begin to sync with each other. This can be seen on line 242 in this file, as an example.

- For better logs with more explicit file transferring, see below.

This is toward the end of peer D's "catching up" phase. It previously was receiving a high number of files (at first 27 are missing of 40), then later is only missing 1-2 files per peer sync.
It is also shown that peer D is communicating with all other peers A-G, which were started at various times or simultaneously with peer D.

See the pdf in this folder for a drawn diagram of the peer communication. The logs are in the logs_scale folder.

The system *did* end up being fully connected, as each peer chose to talk to all existing peers upon joining.
Each connection was also reciprocated with an attempted sync, even though not many were successful as usually one peer was entirely better updated than the other.
The numbers in the file represent the general proportion of the 40 test files which were distributed through a particular connection. They are approximate, because my file selection was randomized and varied.

My file selection was as follows:
- take note of all peers known to be active on the catalog
- for each peer:
    - compare my files to the ones on the peer and find what I'm missing
    - download 1/(known_peers) of these missing files from this peer, randomly choosing which
    - move on to next peer

This resulted in a randomized slow accumulation of files accross the network rather than stopping and updating entirely based off of one peer.
In an active network where peers were constantly adding files, this would help the speed with which it would be found by another peer, as no one peer-to-peer interaction is taking a long time.
Additionally, if a lot of files were dropped at once to a single peer in this network, each other peer would sync a random chunk of them before turning to another peer and syncing some of those, distributing the load rather than
having all of the uploading done by the first peer to all other peers.

Some things which I could do to improve the system or adapt it depending on context:
- Set a minimum for the number of files to be transferred in an interaction (if available for transfer), to prevent the 1 or 2 files transfers that finish out the syncing.
- Dial in the delays depending on latencies and the activity of the system to get fast syncing without performance issues (such as overworking peers with rapid syncings)
