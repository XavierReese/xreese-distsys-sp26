3. Implemented Features

- Name Registration

I relatively quickly set up a thread on the server side to send a simple update message.
On the client side, I used a classmethod to set up an alternate way to initialize the client class,
using a project name, which would then be found within the catalog to locate the host/port.

I came back to this stage to fix and refine things throughout the other two sections. I added a
discover() method that shares code with my new classmethod, allowing a re-searching of the catalog
when the server isn't responding. The most challenging fix was to add logic to choose the most-recently-heard-from
option if there were multiple entries with my project name. There was a new entry every time a new port was given,
so this step was quite necessary.

- retry

The most challenging part of this feature was designing the pattern to retry events upon failure. I ended up with a
delay variable which would double each time, and be capped at 128 seconds. I also had to ensure that no failures would
"escape" the client and be returned to the user, instead it would launch the client into another retry.

Once I had the pattern, I applied this to the discover, connect, and sending/receiving functions. When the send/receive fails,
it retries connection to the socket. When that fails, it searches for the most recent port from the catalog, so I can ensure
that the client is always acting upon the most recent information about the server available

- get_description()

For this feature I was able to mostly make additions to previous logic which separately directed requests based on methods.
I did add a "peers" set of the server. Every new peer that joins gets added and when the description is requested all peers are returned.
My previous organization of the methods made no particular part of this very challenging.
